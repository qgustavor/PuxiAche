# Contributing to PuxiAche

Thanks for helping out! This document covers the stack, project layout, and how to add
translations. For gameplay instructions, see [README.md](./README.md).

## Stack

- **Vue 3** (Composition API) + **Vite**
- **vue-i18n** for translations
- **three.js** for the 3D globe/scene, **d3-geo** for boundary projection and containment tests
- **Turf.js**, used offline-only by `scripts/build-countries.mjs` to build the country
  boundary/buffer data from a public GeoJSON source
- **Firebase Realtime Database**, for the leaderboard and audit trail, accessed via its
  plain REST API rather than the Firebase SDK — see `src/firebase.js`. Required for a
  deployed build — see `.env.example`.
- **anime.js**, for HUD animations

## Project layout

You need Bun and the Firebase CLI's Java-dependent Realtime Database emulator (the JDK
just needs to be on your PATH; `bun run dev` runs the emulator for you). Run `bun run dev`
to start the dev server — it starts Vite and the Firebase Local Emulator Suite together, so
the leaderboard and audit trail work locally with no `.env` file and no real Firebase
project. A deployed build isn't optional about this: it needs real Firebase project config
in `.env`, filled in from `.env.example` (see the note in that file, and `firebase.json`
for the emulator config). The country boundary data is generated ahead of time and checked
into `src/data/`; you only need network access and `bun run build:countries` if you want to
regenerate it (see the comment at the top of `scripts/build-countries.mjs`).

- `src/App.vue` — top-level screen/state orchestration
- `src/components/` — one file per screen/UI piece
- `src/game.js` — round selection, scoring, timing
- `src/globe.js` — the three.js scene (globe, camera, drag/keyboard controls, backdrops)
- `src/geo.js` — lat/lon ⇄ 3D coordinate math
- `src/data/` — country boundary/name data, generated by `scripts/build-countries.mjs`
- `src/i18n.js`, `src/locales/` — translations

## Contributing rules

- No refactoring narration in code comments. Comments should describe what the code
  does and why, for whoever reads it next — not what it used to do, who changed it, or why a
  past approach was rejected. That history belongs in commit messages and PR descriptions,
  not permanently embedded in the source.
- Keep player-facing text (README, in-game copy) free of implementation details. Say what
  the player needs to know to play, not how a feature is built — e.g. "drag to rotate", not
  "drag to rotate, with inertia on release".
- Avoid comments that will silently go stale as the code around them changes (e.g. don't
  enumerate a file's dependencies or a fixed step count in a comment if that's likely to
  change — describe the file's purpose instead).

## Adding a translation

1. Add a new locale JSON file under `src/locales/` and translate every string.
2. Register it in `src/i18n.js`: import the file, add it to `messages` and add the language
   code to `SUPPORTED_LANGS`.
3. Add the locale code to `NAME_LOCALES` in `scripts/build-countries.mjs` and re-run
   `bun run build:countries` to regenerate `src/data/countries.meta.json`.
